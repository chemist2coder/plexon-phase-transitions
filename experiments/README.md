# experiments/ — GPU-варианты (PyTorch/CuPy)

Здесь лежат GPU-версии глубокого расчёта. Они запускались, работали корректно, но **не дали ускорения** по сравнению с CPU. Финальные результаты получены на CPU (см. `src/`).

- `simulation_4conn_CUDA.ipynb` — 4-связность на CuPy.
- `simulation_yukawa_GPU.ipynb` — Юкава на GPU (PyTorch/CuPy).

## Итог (честный отрицательный результат)

GPU-версии считали **не быстрее** CPU, поэтому основной репозиторий использует CPU-скрипты. Это задокументировано намеренно: отрицательный результат тоже полезен.

## Почему GPU не помог (анализ)

1. **Алгоритм Метрополиса последовательный по своей природе.** Каждый обмен занятого и пустого узла зависит от предыдущего состояния и от решения «принять/отклонить». Основной цикл не распараллеливается — GPU нечего делать параллельно.
2. **Решётка 100×100 слишком мала.** Накладные расходы на запуск GPU-ядер и на передачу данных между CPU и GPU превышают время самого вычисления.
3. Быстро на GPU здесь только свёртка (`F.conv2d`), но она не является узким местом расчёта.

## Вывод

Для последовательного Монте-Карло на маленькой решётке GPU — неподходящий инструмент. GPU станет полезен для **3D-версии** (решётка 100³) с векторными обновлениями.
